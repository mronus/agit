Git Provenance Record Format
============================

The provenance extension attaches AI provenance to commits: which lines
of a commit were written by an AI agent, by a human, or by both, and the
reasoning that led to the change.  This document specifies how that data is stored in
a repository and what `git provenance verify` checks.

Provenance is stored next to history, not inside it.  Records are
ordinary blobs reachable from dedicated refs, keyed by the object id of
the commit they describe.  Commit objects are not changed, so adding,
fixing or removing a record never rewrites code history, and a
repository with records stays a valid Git repository that works with
any Git implementation.


Ref namespace and layout
------------------------

Two refs hold provenance data:

`refs/provenance/lines`::
	Line records.  Small, structured and meant to be public alongside
	the code.

`refs/provenance/reasoning`::
	Reasoning records.  Potentially large and sensitive, kept under a
	separate ref so that they can be transferred, kept local or purged
	independently of line records.

Each ref is a notes ref.  Its layout is exactly the one used by
linkgit:git-notes[1]: the ref points to a commit whose tree maps the
object id of a code commit to a blob, using the same fan-out
(`ab/cdef...`) that notes use.  A record for commit `C` is therefore
the note attached to `C` in the respective notes ref, and the history
of the ref is an audit log of changes to the records.

There is at most one line record and at most one reasoning record per
commit.  A commit without a record is not an error; it simply has no
provenance (for example, history recorded before the extension was in
use, or commits made with stock Git).


Common rules
------------

Both record types are text in UTF-8 with LF line endings.  Each line
starts with a keyword, followed by a single space and its arguments.
Unless stated otherwise, blank lines and lines starting with `#` are
ignored.

Object ids are written in full, as lowercase hexadecimal, in the hash
algorithm of the repository.

The first line that is not ignored is `version <n>`.  This document
describes version 1.  A reader must reject a record with a version it
does not understand.


Line record, version 1
----------------------

A line record describes which lines a commit added or removed and who
wrote them.

------------
version 1
commit <object id of the code commit>
capture (observed git/<version> | declared | adopted)
actor <id> ai model=<model> tool=<tool> session=<session> source=(observed | declared)
actor <id> human ident=<ident>
file <path>
+ <a>[-<b>] <mark> <actor-ids> <anchor>
- <a>[-<b>] <mark> <actor-ids> <anchor>
------------

The `version`, `commit` and `capture` lines come first, in that order.
They are followed by zero or more `actor` lines, then zero or more
`file` blocks.  A `file` block is a `file` line followed by zero or
more range lines (`+` or `-`) for that path.

`commit <object id>`::
	The object id of the code commit the record describes.  It must
	be the commit the record is attached to.

`capture <how>`::
	How the record was produced:
+
--
`observed git/<version>`;;
	The program that wrote the record observed the changes while
	they were made.  The token after `observed` names that program
	and its version, as `<tool>/<version>`; for Git it is
	`git/<version>`.  Readers treat the token as opaque: it must
	contain a `/` with text on both sides and no spaces.
`declared`;;
	The record was declared by a tool or person, not observed.
`adopted`;;
	The record was re-attached to a commit the extension did not
	record (for example after a rewrite done with stock Git or by
	another tool).  Only adopted records may contain `UNKNOWN`
	ranges.
--

`actor <id> ai model=<model> tool=<tool> session=<session> source=<source>`::
	Declares an AI actor.  `<model>`, `<tool>` and `<session>` must
	not contain spaces.  `<source>` is `observed` or `declared`.  The
	four fields appear in this order.

`actor <id> human ident=<ident>`::
	Declares a human actor.  `<ident>` is the rest of the line, for
	example `A U Thor <author@example.com>`.

`file <path>`::
	Starts the block of ranges for `<path>`, a path relative to the
	top of the tree.  The path is the rest of the line.  Paths that
	contain a LF cannot be represented in version 1; a writer must
	not produce a record for them.

`+ <a>[-<b>] <mark> <actor-ids> <anchor>`::
	Lines `<a>` to `<b>` of `<commit>:<path>` (the post-image) were
	added by the commit.

`- <a>[-<b>] <mark> <actor-ids> <anchor>`::
	Lines `<a>` to `<b>` of `<first parent>:<path>` (the pre-image)
	were removed by the commit.

Actor ids are made of non-space characters other than `,` and must
not be `-`.  Each id is declared at most once.

Line numbers are 1-based and the range is inclusive; `<a>` alone means
the single line `<a>`.  Line numbers are written in decimal without
leading zeros.  `<actor-ids>` is a comma-separated list of
declared actor ids, or `-` for an `UNKNOWN` range.


Marks
~~~~~

`AI`::
	The text is exactly as an AI agent produced it.

`MIXED`::
	An AI agent produced the text and a human edited it, or the
	reverse.

`HUMAN`::
	The commit was made with provenance enabled and no AI agent
	touched the lines.

`UNKNOWN`::
	The origin of the lines is not known.  Only valid in a record
	with `capture adopted`; never used in a record written at commit
	time.


Anchors
~~~~~~~

The anchor of a range is the object id of a blob whose content is the
exact bytes of the lines in the range, including their newline
characters, computed with the hash algorithm of the repository.  It is
the value that

------------
printf '%s' "<bytes of the lines>" | git hash-object --stdin
------------

prints.  The blob is never written to the object database.

Anchors make a record self-checking: a record that does not match the
content of its commit is detected by recomputing them.  They also
allow a later version of the extension to find the same content in a
rewritten commit and re-attach the record to it.


Reasoning record, version 1
---------------------------

A reasoning record says why a commit was made.

------------
version 1
commit <object id of the code commit>
session <id> model=<model> tool=<tool> [started=<unix-ts>] [ended=<unix-ts>]

<free-form summary text>
------------

The `version` and `commit` lines come first, in that order, followed by
zero or more `session` lines, each naming one AI session that took part
in the change.  A record with no `session` line states that no AI was
involved.  The first blank line ends the header; everything after it is
a free-form summary in UTF-8, meant to be read by humans, and is not
subject to the "ignored lines" rule above.

The design calls for a reasoning record to be a tree, holding the
summary together with per-session metadata and optional transcripts,
so that pieces can be fetched or redacted on their own.  Version 1
stores only a single blob; the tree form is deferred to a later
version of this format.


Verification
------------

`git provenance verify` checks a line record against the commit it is
attached to.  It reports the first failure it finds and checks that:

1. the record parses as a version 1 line record;

2. the `commit` line names the commit the record is attached to;

3. every actor id used by a range is declared by an `actor` line;

4. every mark is one of `AI`, `MIXED`, `HUMAN` or `UNKNOWN`, and
   `UNKNOWN` ranges appear only in records with `capture adopted`;

5. for each `+` range, `<path>` is a regular file in the tree of the
   commit, `1 <= <a> <= <b> <= <number of lines>`, and the anchor
   matches the lines;

6. for each `-` range, the commit has a first parent, `<path>` is a
   regular file in the tree of that parent, and the same bounds and
   anchor checks hold in the parent's version of the file.

Whether the ranges cover exactly the lines changed by the commit, and
the content of reasoning records, are not verified yet.
