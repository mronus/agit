Git Provenance Design Notes
===========================

Provenance is an extension to Git that records where the contents of
a commit came from. Two pieces of information are recorded:

1. The AI reasoning behind each commit: which agent sessions
   contributed to it and the summary they produced.

2. For each changed line range in a commit, whether the lines were
   written by an AI agent, by a human, or by both.

The extension ships in agit, a distribution of Git (see "Releases"
below). In this document, "a git with provenance" means a Git built
with this extension and "stock Git" means one without it.

Stock Git is the standard the extension builds on. A repository with
provenance records must remain a valid Git repository that works with
existing hosting services, CI systems, editors and with collaborators
who use stock Git, and enabling provenance in an existing repository
must require no conversion step. This constraint drives most of the
design below.

Objective
---------
Record per-commit reasoning and per-line provenance for every commit
made with provenance enabled, using only facilities that stock Git
already transfers, stores and garbage-collects correctly, so that
provenance is never lost or rejected by a peer that does not know
about it.

Background
----------
Git stores history as a graph of immutable, content-addressed objects
and finds them by walking pointers outwards from refs. Every operation
that works on history -- `log`, `fetch`, `push`, `gc`, `fsck` -- is a
variation of that walk. A new kind of object pointer therefore has to
be taught to every walker (`revision.c`, `list-objects.c`,
`reachable.c`, the commit-graph, reachability bitmaps, `fsck`,
`upload-pack`, `index-pack`) before the data it points to is safely
transferred and kept alive. Stock Git, and every hosting service built
on it, would ignore such a pointer, prune what it points to, and
reject packs containing an unknown object type.

Git does, however, already have a mechanism for attaching mutable,
optional data to commits without touching them: notes
(linkgit:git-notes[1]). A notes ref points at a tree that maps a
commit's object id to a blob, laid out as a fan-out tree that scales
to millions of entries. Because the data is reachable from an ordinary
ref, every version of Git transfers it, keeps it alive and verifies it
without changes. Provenance records use this mechanism.

Documentation/technical/git-architecture.adoc describes Git's
structure from this point of view and lists what a new commit-attached
object would have touched. "Alternatives Considered" below summarises
why that route was rejected.

Goals
-----
1. Every commit made with provenance enabled carries a reasoning
   record and a line provenance record.

2. Line provenance distinguishes AI-written, human-written and mixed
   lines at line granularity, and can be queried for any line of any
   snapshot through `blame`.

3. An existing Git repository needs no conversion: no repository
   format extension, no rewritten history.

4. A repository with provenance records is a Git repository as it is.
   Hosting services, stock Git clients and other Git implementations
   handle it unchanged; they merely do not see the provenance.

5. Provenance survives history rewriting done by a git with
   provenance (amend, rebase, cherry-pick, squash) and can be
   re-attached after rewriting done by tools that know nothing about
   it (server-side squash merges, `filter-repo`).

6. Reasoning can be removed or kept private after the fact without
   rewriting code history, because it may contain secrets.

7. Agents integrate with two command invocations per edit and no
   further knowledge of the extension.

Non-Goals
---------
1. Proving that a human wrote a line. Provenance is self-reported by
   the capture tooling; the extension can detect records that no
   longer match their commit, not records that lied.

2. Secret scanning, redaction or push protection. Git leaves these to
   hosting services and pre-commit tooling, and so does this
   extension.

3. Character-level attribution. Marks are per line.

4. Attribution of edits the extension was not told about. Lines in a
   commit made with provenance enabled that no stamp covers are human
   by definition; commits made without it are unknown.

5. A new object type, a new commit header, or any change to the
   object, pack or wire formats.

6. Agent- or editor-specific integration code. The extension defines
   a tool-agnostic protocol; adapters for particular agents and
   editors are maintained in a separate repository.

Overview
--------
Provenance is stored as ordinary blobs under two refs, keyed by the
object id of the commit they describe, using the notes tree layout:

....
 refs/heads/main -----------> c2 --> c1 --> c0   code history, unchanged

 refs/provenance/lines -----> fan-out tree --> <c2> : line record of c2
                                               <c1> : line record of c1

 refs/provenance/reasoning -> fan-out tree --> <c2> : reasoning record of c2
                                               <c1> : reasoning record of c1

 c0 has no record: it predates the extension, so its lines are UNKNOWN.
....

The records are not part of a commit's identity. Attaching, correcting
or purging them never changes a commit id.

The hard part is capture: Git sees only the final content of a commit
and cannot know who typed what. The extension therefore keeps a small
local journal, similar in spirit to the index, in which AI agents
record snapshots of files immediately before and after they write to
them. At commit time git runs a blame over the chain of snapshots and
derives the marks. Agents never describe what they changed, only when.

Git commands then make the records first-class: `commit` writes them;
`diff`, `show`, `log` and `blame` display them; `rebase` and friends
remap them; `fetch` and `push` carry them by default; and
`provenance verify` checks them.

Detailed Design
---------------

Refs and records
~~~~~~~~~~~~~~~~
Two refs are used rather than one, split by sensitivity and size:

`refs/provenance/lines`::
	Line provenance. Small, structured, not sensitive, needed by
	`blame` and `diff`. Meant to travel with the code.

`refs/provenance/reasoning`::
	Reasoning. Potentially large and sensitive. Can be pushed to a
	different remote than the code, fetched lazily, or not kept.

Each ref points to a commit whose tree is a notes fan-out tree mapping
a code commit's object id to its record. The ref's own history is an
audit log of provenance changes and can be rewritten, for instance to
purge a transcript, without touching code history.

The on-disk formats are specified in
Documentation/technical/git-provenance-format.adoc. The following
subsections describe what they contain and why.

Line record
~~~~~~~~~~~
One record per code commit. It names the capture mode, the actors
involved, and for each changed file the line ranges of the commit's
diff against its first parent, with a mark and the actors responsible:

....
version 1
commit <object id>
capture observed git/<version>
actor a1 ai model=<model> tool=<tool> session=<session> source=observed
actor h1 human ident=<ident>
file src/foo.c
+ 10-24 AI a1 <anchor>
+ 25 MIXED a1,h1 <anchor>
+ 26-30 HUMAN h1 <anchor>
- 40-45 AI a1 <anchor>
....

- Added ranges (`+`) are in post-image coordinates; deleted ranges
  (`-`) are in pre-image coordinates, so that "an agent removed this
  code" can be shown as well.

- Actors separate who did something (model, tool, session, human
  identity) from what kind of actor it was, so "which lines did model
  X write" is answerable without changing the mark vocabulary.

- The capture mode records how the marks were obtained: `observed`
  (from stamps, see "Capture"), `declared` (claimed by an agent at
  commit time without stamps) or `adopted` (re-attached after a
  foreign rewrite, see "Re-anchoring"). Consumers can weigh the marks
  accordingly.

- The anchor of a range is the blob object id of the exact bytes of
  the lines in the range. It is what makes records self-healing: after
  a rewrite that the extension did not see, the same content can be
  found in the new commit and the marks carried over. It also lets
  `verify` detect a record that no longer matches its commit.

- Merge commits record only conflict resolutions and other changes
  present in neither parent; lines that merged cleanly keep their
  provenance through `blame`.  Until this is implemented, a merge
  concluded with `git commit` is recorded against its first parent,
  like any other commit.

- Binary files get a single file-level mark.

Reasoning record
~~~~~~~~~~~~~~~~
One record per code commit, listing the agent sessions that
contributed at least one surviving line, with model, tool and
timestamps, followed by the summary the agent wrote. A commit made
with provenance enabled to which no session is attached gets no
reasoning record, which states that no AI was involved.

Full transcripts are optional, policy-controlled
(`provenance.reasoning.transcripts`), and the first thing to drop for
privacy. The initial implementation stores the reasoning record as a
single blob; storing sessions and transcripts as separate blobs under
a per-commit tree, so that they can be fetched and purged
individually, is future work.

Marks
~~~~~
`AI`::
	The text is as an AI agent produced it.

`MIXED`::
	An agent produced it and a human edited it afterwards, or the
	reverse. Any touch counts (`provenance.mixed.threshold` defaults
	to 0); a higher threshold compares the old and new line with a
	similarity metric so that a line rewritten wholesale goes to the
	new actor.

`HUMAN`::
	The commit was made with provenance enabled and no stamp covered
	the line.

`UNKNOWN`::
	The extension did not watch the line being written. No record
	exists for the commit, as it predates the extension or was made
	with stock Git; or a rewrite took the line from such a commit
	(see "History rewriting"); or re-anchoring could not match it
	(see "Re-anchoring").

In `diff` and `blame` output the marks are shown as a one-character
gutter column: `A`, `M`, `H` and `?`.

Capture
~~~~~~~
The information "who changed this line" exists at exactly one moment,
while the change is being made; everything later is reconstruction.
The extension therefore captures at edit time and only assembles at
commit time.

Agents talk to git through one command, `git stamp`. Only the agent
side ever calls it; the human calls nothing, and human edits are
inferred by elimination.

`git stamp begin --session <id> [--model <m>] [--tool <t>] [<paths>]`::
	Called by the agent's harness (a hook) immediately before the
	agent writes to files. Snapshots the current content of
	`<paths>`, or of the whole working tree if none are given, into
	the journal.

`git stamp end --session <id> [<paths>]`::
	Called by the harness immediately after the write. Snapshots
	again; the difference between the two snapshots is an AI interval
	owned by the session.

`git stamp edit --session <id> --path <path> --pre <file> [--post <file>]`::
	Called by a harness that reports an edit after making it, rather
	than calling `begin` and `end` around it. `--pre` holds the
	content of the path before the edit and `--post` the content
	after it, defaulting to the file in the working tree; the
	difference is an AI interval. Git has no parser for the edit
	descriptions that harnesses exchange, so a harness whose payload
	carries only the old and new text reconstructs the pre-image by
	undoing the edit on the file on disk. Observed-quality, like
	`begin`/`end`.

`git stamp reason --session <id> --summary <file> [--transcript <file>]`::
	Called by the agent when it finishes a task. Stores the reasoning
	for the session in the journal.

`git stamp claim --session <id> (<paths> | --patch <file>)`::
	Called by an agent at commit time when it has no stamps. Records
	the named paths or hunks as AI for the session, flagged
	`declared`.

A snapshot is an ordinary blob or tree written to the object database,
as `git stash create` does for the working tree. Unchanged files cost
nothing because their blobs already exist, and whole-tree snapshots
use the same stat cache and fsmonitor as `git status`. Whole-tree
snapshots are the default because they also catch edits made through
shell commands, formatters and generators the agent ran. Sessions are
independent, so parallel agents use distinct session ids; overlapping
AI intervals are still `AI`. Journal entries live in the worktree's
git directory, are never transferred, and are deleted once a commit
consumes them. An `end` without a preceding `begin` diffs against the
last snapshot of any session (or the first parent), which is exact
unless a human edited the same file in between; harnesses that only
offer an after-edit hook should prefer `stamp edit` when their payload
carries the edit.

The protocol is deliberately agent-agnostic: the extension knows
nothing about any particular agent or editor, and this repository
contains no adapters. For an agent with tool-use hooks, an adapter is
two hook entries calling `begin` and `end`. For editors, agent-style
edits map to the same calls through the editor's hooks; inline
completions need an extension that watches document changes, and are
only as good as the events the editor exposes. Commits made from an
editor's source-control interface record provenance when the editor's
git executable is a git with provenance. Adapters are maintained in a
separate repository.

The possible moments to capture, and what each one can know:

....
 moment              who acts     what git can know
 ------------------  -----------  -----------------------------------
 edit time           harness      exact pre/post content of every AI
                                  edit; human edits by elimination
 staging (git add)   git          content being staged; cannot tell
                                  AI from human on its own
 commit time         agent/human  session id and summary; with the
                                  journal, the full edit history
 commit, no journal  agent        only the claim "I made this commit"
 after commit        tooling      a patch to attach to an existing
                                  commit; mixed lines can no longer
                                  be separated
....

Stamp at edit time, assemble at commit time, repair after commit.

Attribution
~~~~~~~~~~~
For each staged file, git takes the version chain from the `HEAD`
blob through the journal's snapshots to the staged blob, each step
labelled with the actor of its interval, and runs an incremental blame
over that chain using `xdiff` and the core of `blame.c`:

1. Every line of the staged blob is traced to the step that last
   introduced it. That step's actor sets the base mark.

2. When a step replaces lines rather than adding new ones, each
   replaced line whose previous owner was a different actor becomes
   `MIXED`. With a non-zero `provenance.mixed.threshold`, the old and
   new line are compared with a similarity metric (as `--word-diff`
   does) and a line rewritten wholesale goes to the new actor instead.

3. Lines present in the working tree but not staged are not in the
   staged blob and are excluded; `git add -p` needs no special
   handling.  The commit consumes their stamps all the same, unless
   it is a partial commit (a pathspec, `--only` or `--include`), so
   these lines are `HUMAN` when they are committed later.

4. A changed file with no journal entries is `HUMAN`: the commit is
   being made with provenance enabled, so the absence of a stamp is
   the evidence.

The reasoning record collects every session whose stamps contributed
at least one surviving line. Sessions whose work was entirely
discarded are not attached (configurable).

Commit
~~~~~~
Git computes both records just before the commit object is written,
once the message is final and the hooks have run. Once the commit
object is written, it stores the records and updates
`refs/provenance/lines` and `refs/provenance/reasoning` in the same
ref transaction as the branch, so either all refs move or none do.
The notes commits that carry the records are authored and committed
by the committer ident of the commit, not by the environment's
author, which a rebase may leave unset or unparsable.
The journal is then emptied, except after a partial commit.
`provenance.enabled` (on by default) turns all of this off.

`--session <id>` is how an agent that commits identifies itself. Git
attaches that session's reasoning; if the journal has stamps for the
session they are used as normal; if it has none, git warns, names the
session, points to `git stamp claim`, and falls back to `declared`
attribution: claimed lines are `AI`, the rest `HUMAN`. If the agent
ignores the warning, everything is `AI` (declared).

A commit made without `--session`, and to which no stamps contributed,
is recorded with no sessions. Git then prints an advice message
(`advice.provenanceSession`) saying that if the change came from an
LLM session, its details can be provided with `--session`. The message
names the option and nothing more, and is silenced with the usual
advice configuration. It is not printed when stamps already link the
commit to sessions.

`provenance.require` turns that advice into an error and refuses to
make a commit that no session is linked to, for teams that want
guaranteed coverage.

Viewing
~~~~~~~
- `--provenance` is a diff option, so `diff`, `show`, `log -p`,
  `diff-tree -p` and every other command that shows a patch accept
  it. It inserts the mark of each line before its `+`/`-` marker, and
  a space before context lines. Combined diffs and `--word-diff`
  output get no column, and `format-patch` rejects the option: its
  output is meant to be applied, and a patch with the column cannot
  be.

- When a patch shows a commit against its first parent (the parent
  named in the commit object, whatever the history walk did to it),
  or a root commit against the empty tree, the marks come from the
  commit's line record: a `+` line takes the mark of the `+` range of
  the `file` block of its new path that contains its line number, a
  `-` line that of the `-` range of the block of its old path. A
  rename is recorded as a deletion and an addition, so with rename
  detection the added lines of a renamed file are found under its new
  path and its removed lines under its old one; the source of a copy
  gets no marks. The record is read and parsed once per commit shown.

- When the post-image is the index or the working tree and the
  pre-image is `HEAD`, the marks come live from the journal, through
  the attribution walk of `git commit` run one path at a time on the
  content the diff has in memory, without writing objects or touching
  the index: `git diff --cached` shows exactly the marks `git commit`
  would record, and `git diff HEAD` those `git commit -a` would
  record. `git diff` compares the index with the working tree; it
  marks each added line as the attribution of `HEAD` against the
  working tree marks it, and shows its removed lines, which are lines
  of the index that the journal cannot speak for, as `?`.

- Every other line is `?`: lines of a diff between arbitrary commits
  or of a merge against a parent other than the first, of a commit
  without a record, of a path without a block, outside every range, of
  a live diff when `provenance.enabled` is false, and lines shown
  through a `textconv` filter. `A`, `M` and `H` are shown only where a
  record or the journal says so, and a missing or malformed record
  never makes a diff fail.

- `blame --provenance` shows the mark after the commit name. `blame`
  already finds the commit that introduced a line and the line's
  number in that commit; the mark is that of the `+` range of the
  commit's record for that path and line, or `?` if there is none,
  as for lines that `-M`, `-C` or `--ignore-rev` attribute to a
  commit that did not add them. The porcelain formats add a
  `provenance-mark` line and a `provenance-actor` line per actor, as
  the record declares it. Records are cached per commit.

- The pretty formats gain `%(provenance:summary)`, the summary of the
  reasoning record, `%(provenance:share)`, the share of the added
  lines that are `AI` or `MIXED`, and `%(provenance:models)` and
  `%(provenance:sessions)`, the models and sessions of the AI actors
  of the line record.

- `provenance show` prints a commit's records; `provenance verify`
  checks that records parse, refer to paths and ranges that exist,
  and that anchors match.

History rewriting
~~~~~~~~~~~~~~~~~
Git already copies notes across rewrites (`notes.rewrite.*`,
`notes.rewriteRef`), but a copied record would describe the diff of
the old commit, not that of the new one. The extension instead
computes the records of a rewritten commit from those of the commits
it rewrites, its sources, with the attribution walk of `git commit`.

The chain of versions of each changed file gets one step per source
whose line record has a block for the file, or, for a source without
a line record, that changes the file, before the steps of the
journal. In such a step the owners of the lines it changes come from
the record instead of a single actor. With one source:

....
 new parent --------> first snapshot -------> ... -------> new blob
            marks of             stamped            the
            the source           session            human
....

Without journal entries for the file, the step goes from the new
parent to the new blob directly.

- The changes of a source are found by comparing its post-image with
  the version the step goes to, which for a cherry-pick holds the
  same changes on top of a different parent. A line kept from the
  source has the actors of the `+` range that covers it; a line that
  replaces a covered line gains the human, so a conflict resolution
  that rewrites an AI line is `MIXED`; every other line, such as one
  that differs only because the parents differ, is the human's.

- A line of the new parent that the step deletes is owned in the same
  way, by comparing the pre-image of the source with the new parent
  and using its `-` ranges.

- A source without a line record, made with stock Git or before the
  extension was in use, counts as one whose record marks every line
  it adds and every line it deletes `UNKNOWN`. The lines of such a
  source, like those of an `UNKNOWN` range of a record, stay `UNKNOWN`
  wherever they are kept or replaced: `MIXED` would claim that an
  agent and a human both wrote a line whose origin was never seen.
  The other actors of such a line are not listed, and a session does
  not get attached to the commit through it.

- The journal is used and emptied as by `git commit`, so stamps made
  while resolving conflicts count.

- AI actors of the source records keep their ids and metadata; the
  first record that declares an id wins. The human is the author of
  the new commit, and `capture` names the git that did the rewrite.

How each rewrite uses this:

amend::
	The commit being amended is the source. Lines unchanged since
	the old commit keep their marks; lines changed since then belong
	to the session whose stamps changed them or to the human, and
	deletions keep their marks where they survive. Reasoning
	is the union of the old record's sessions and those the journal
	attaches, with the summaries in that order. The lines that an
	amended commit without a line record, made with stock Git, added
	are `UNKNOWN`; those the amendment adds are marked as in any
	commit.

cherry-pick, rebase (pick, reword, edit)::
	The picked commit is the source. Reasoning is copied as is,
	followed by sessions the journal attaches.

squash, fixup::
	`HEAD`, which the new commit replaces, and the commit squashed
	into it are the sources, in that order; the chain goes through
	the post-image of `HEAD` first. A line that the later commit
	rewrote gets the actors of both. The lines of a commit without a
	line record are `UNKNOWN`, and those of the other keep their
	marks. Sessions are listed once and summaries concatenated.

revert::
	The sides swap: the lines the revert deletes get the marks of
	the `+` ranges of the source. The lines it restores, those of
	the source's parent that the source deleted, get the marks of
	whoever wrote them: a blame of the parent, as `git blame` runs
	it (following renames), finds the commit that introduced each
	line, and the line takes the actors of the `+` range of that
	commit's line record that covers it. A line whose commit has no
	line record, or whose range is `UNKNOWN`, is `UNKNOWN`; a human
	of that record is the human of the revert. This costs one blame
	per file the source changes, which is acceptable as reverts are
	rare. Reasoning comes from the journal only, as the source's
	reasoning explains the change, not its revert.

A rewrite writes a record even if none of its sources has one: the
lines it takes from them are `UNKNOWN`, and the lines it adds itself,
such as those of a conflict resolution, are attributed as by `git
commit`, since the extension did watch those being written. A record
that does not parse is ignored with a warning, as if the source had
none. Records are written in the ref transaction
that moves `HEAD`, by `git commit`, by the sequencer
(`cherry-pick`, `revert`, the merge backend of `rebase`), and by `git
am` for `rebase --apply`, where `rebase-apply/original-commit` names
the source. When the sequencer runs `git commit` to let the user edit
a message, it names the source with a hidden option, as nothing else
does for a clean revert or a squash; `git commit` run by hand finds it
through `CHERRY_PICK_HEAD` or `REVERT_HEAD`.

When `rebase -i` stops at a `fixup` or `squash` whose changes
conflict, the user may conclude it by hand instead of with `rebase
--continue`. `git commit` then finds that command's commit, as
`rebase-merge/stopped-sha` names it and it is the last of
`rebase-merge/current-fixups`, as long as `HEAD` is still the commit
the rebase stopped with. `git commit --amend` gets the sources that
`rebase --continue` would give it, `HEAD` and then that commit, and a
plain `git commit` takes the commit as a pick, whose changes are found
in the new commit. The following `rebase --continue` finds nothing
left to commit and leaves the records alone.

`cherry-pick --no-commit` makes no commit and writes no
`CHERRY_PICK_HEAD`, so it lists the commits it applies in a `picks`
file next to the journal (see the format document). The next `git
commit` takes them as sources after the commit being amended and the
one being picked, in the order they were applied, all found in the
new commit, so that several `-n` picks followed by one commit carry
the records of each. Every commit that empties the journal removes
the file with it. As the user may have discarded a
pick before committing, such a source is tentative: its reasoning is
attached only if a line of the commit takes its owners from it, as
for `adopt`. A revert takes no picks; `revert --no-commit` writes
`REVERT_HEAD`, which names the last commit reverted only.

Not covered yet: merges recreated by `rebase --rebase-merges`,
`git replay`, `git history`, and `git am` of mailbox patches, which
have no source commit. Rewrites by tools that do not know the
extension leave commits without records, which `git provenance adopt`
repairs (see "Re-anchoring").

Re-anchoring
~~~~~~~~~~~~
Rewrites the extension did not see -- stock Git rebases and
cherry-picks, a hosting service's "squash and merge", `filter-repo` --
produce commits with no record, although the records of the commits
they were made from usually exist, locally or fetched with
`refs/provenance/lines`. `git provenance adopt <revision-range>`
repairs them, oldest first:

1. The candidate sources of a commit are the commits that have a line
   record, restricted with `--from <rev>` to those that `<rev>` can
   reach. A candidate in the history of the commit is not its source;
   one walk from all the commits being adopted finds those. Of the
   rest, those whose record has a block for a path the commit changes
   are its sources, oldest commit date first. No diff of a candidate
   is needed for this.

2. The attribution walk of "History rewriting" runs with these
   sources, all found in the commit, and no journal. Lines are matched
   by content, as for a cherry-pick, so a rewrite with the same patch
   as its source gets all of its marks. A line the commit changes
   takes the owners of the first source that has it as it is among
   the lines its record covers, or failing that of the first that has
   a line it replaces; the same goes for the lines it deletes:
+
....
 first parent ------------------------------------> adopted commit
              marks of all sources, found together
....

3. A line that no source accounts for, or that replaces a line of a
   source, is `UNKNOWN`. `HUMAN` is never guessed: a line is `HUMAN`
   only if a source record marks it so, and its human is then the
   author of the commit.

4. The reasoning record collects the sessions and summaries of the
   sources that some line of the commit was taken from, in the same
   order.

The resulting record is marked `adopted`. If no source accounts for
any line, nothing is written: an all-`UNKNOWN` record would only stand
in the way of adopting the commit once its sources have been fetched.
A commit with a record is left alone, except that `--force` replaces
an adopted record; merge commits are not adopted.

Adopting is an explicit action, like `verify`, and does not depend on
`provenance.enabled`.

Transfer
~~~~~~~~
The provenance refs of a remote are fetched into tracking refs, as
branches are fetched into remote-tracking branches:
`refs/provenance/lines` of the remote `origin` lands in
`refs/provenance/remotes/origin/lines`, and likewise for
`refs/provenance/reasoning`. They are not under `refs/remotes/origin/`,
where they would show up as remote branches.

The refspecs are implicit. `fetch` from a configured remote (and so
`pull`, `fetch --all` and `remote update`) adds

....
+refs/provenance/lines:refs/provenance/remotes/<name>/lines
+refs/provenance/reasoning:refs/provenance/remotes/<name>/reasoning
....

to the refspecs it uses, whether they come from the configuration or
from the command line, and `clone` adds them to its initial fetch.
Nothing is written to `remote.<name>.fetch`, so existing clones need
no conversion and `provenance.enabled=false` turns transfer off
entirely. A remote without provenance refs is not an error; the refs
are not written to `FETCH_HEAD`; `--prune` prunes their tracking refs.
Nothing is added for a URL, for `--prefetch`, or for a provenance ref
that the refspecs already map, which covers the `+refs/*:refs/*` of
`clone --mirror`.

After a fetch that updated a tracking ref, the tracking ref is merged
into the local ref, through a ref transaction:

1. If the local ref does not exist, it is created at the fetched
   commit. If the fetched commit is an ancestor of the local ref,
   nothing happens; if the local ref is an ancestor of the fetched
   commit, it is fast-forwarded.

2. Otherwise a merge commit is made, with the local and the fetched
   commit as parents, so that later fetches and pushes are
   fast-forwards. Its tree is a three-way merge of the notes trees
   against their merge base: a record that only one side added,
   changed or removed takes that side's version. Keys are disjoint
   commit ids, so this is almost always a plain union.

3. A record that both sides changed differently keeps the local
   version, with a warning naming the commit. Records are not
   concatenated, as the `cat_sort_uniq` strategy of `notes-merge.c`
   would do, because the result would not parse. If the two sides
   share no history, as in a shallow clone, the merge is a union with
   the same rule.

The merge is written on top of `notes.c` in `provenance-transfer.c`
rather than through `notes_merge()`, whose `ours` strategy resolves
conflicts without reporting them and which prints its progress to
standard output.

`push` to a configured remote pushes the local provenance refs in the
same push as the branches, when it pushes at least one branch and the
local refs exist: not for a URL, `--mirror` (which pushes them
anyway), `--delete`, `--prune` or `--tags` alone. They are forced only
with `--force`. If the remote rejects a provenance ref because it
moved, `push` runs `git fetch` for the rejected refs, which merges
them as above, and pushes the provenance refs once more; if that is
rejected too, the push fails with a hint to run `git fetch <name>`.

Stock Git users can fetch the refs with an explicit refspec, and stock
servers and hosting services need nothing: nothing on the wire
changes.

`provenance.reasoning.fetch` and `provenance.reasoning.push` take
`always` (the default) or `never`. A third value, `ondemand`
(structure now, blobs lazily through partial clone), is reserved: it
needs partial-clone support for reasoning blobs and is rejected until
then. Size is controlled where the data is written, by
`provenance.reasoning.transcripts`.

Shallow clones, bundles and partial clones need no changes to carry
the refs; whether a partial-clone filter should exclude reasoning
blobs is future work.

Maintenance
~~~~~~~~~~~
- `gc` needs no change: everything is reachable from
  `refs/provenance/*`. Records whose code commit is no longer
  reachable can optionally be pruned, as `git notes prune` does.

- `provenance verify` is the `fsck` of provenance.

- `fast-export` and `fast-import` already carry notes, so migrations
  and `filter-repo` can carry records.

- `format-patch` can emit the line record after the `---` separator,
  where stock `git am` ignores it.

Migration and Interoperability
------------------------------
Existing Git repository::
	Works as it is. All past commits are `UNKNOWN`; capture starts
	with the next commit. Nothing is rewritten.

Repository used with stock Git::
	Works. The code is identical; `refs/provenance/*` are extra refs.

Mixed team::
	Commits made with stock Git are `UNKNOWN`; commits made with
	provenance enabled are fully marked. Nothing errors.

Hosting services::
	Unaffected. They cannot render marks, but CI jobs and bots can
	read `refs/provenance/*` and post them.

Removing provenance::
	Delete `refs/provenance/*`. A plain Git repository remains.

The extension does not set `core.repositoryformatversion` or any
`extensions.*`, because nothing it writes would be destroyed or
misread by stock Git. Not needing the repository format extension is
the strongest evidence that the migration goal is met.

Releases
--------
The extension is distributed in agit releases of Git, whose versions
carry an `.agit.<n>` suffix (`git version 2.56.0.agit.1`). The release
and tagging convention is described in the repository's README and in
linkgit:git[1].

Integrity
---------
Git protects history with the hash chain and optional signatures, and
leaves policy -- protected branches, required signatures, audit -- to
hosting services. The extension does the same for provenance:

- Records are not part of a commit's identity. No commitments,
  trailers or headers are added to commits.

- The provenance refs have their own history, so the controls applied
  to code apply to them: protect the refs, require signed pushes, keep
  the audit trail through the ref's history.

- `provenance verify` detects records that drifted from their
  commits.

Provenance is self-reported by the capture tooling. Nothing in Git or
the extension can prove that a human typed a line marked `HUMAN`.

Privacy
-------
Like Git itself, the extension has no built-in secret scanning or
redaction. Scanning and push protection are hosting-service and
pre-commit features, and they apply unchanged because reasoning is
pushed as ordinary blobs under an ordinary ref.

What the extension guarantees is that reasoning is separable, so
those tools have something to act on without touching code history:

- Reasoning lives under `refs/provenance/reasoning`, not in the
  commit. Rewriting or deleting that ref's history changes no commit
  id.

- `git provenance purge <commit|session|pattern>` rewrites only that
  ref. Old blobs then go away by the usual route: force-push the one
  ref and let the host's `gc` drop them.

- `refs/provenance/reasoning` can be pushed to a different remote than
  the code, or not pushed at all.

- The standard hooks apply: `pre-commit` and `commit-msg` on the
  client, `pre-receive` and `update` on the server. Git pushes the
  code ref and the provenance refs in one push, so a server-side hook
  sees both and can reject both.

Performance
-----------
- Commit: the attribution walk covers only changed files and their
  snapshot chains, roughly a few `diff` runs per file.

- `blame --provenance`: one record lookup per distinct commit in the
  output. A fan-out tree lookup is cheap, and parsed records are
  cached for the run.

- Revert: one blame per file that the reverted commit changes, to
  find who wrote the lines it restores.

- `diff --provenance` of uncommitted changes: the journal intervals
  are computed once per diff, then each shown path costs one
  attribution walk.

- Repository-wide queries (AI share over time) can use an optional,
  rebuildable local cache in the spirit of the commit-graph.

- Size: line records are a few hundred bytes per commit. Transcripts
  dominate, which is why they are optional, separate and lazily
  fetchable.

Decisions
---------
The following were decided during design and are reflected above:

1. `MIXED` is line-level with threshold 0: any touch by the other
   actor makes a line `MIXED`.

2. Lines with no stamp are `HUMAN` in any commit made with provenance
   enabled. `UNKNOWN` marks lines the extension never watched being
   written: commits with no record, and the lines a rewrite takes from
   them.

3. Integrity and privacy follow Git's norm: no commitments, scanning
   or redaction inside the extension.

4. Reasoning is fetched by default.

5. Agents report their changes through the `stamp` protocol; the
   harness calls `begin`/`end` around each edit and marks are
   assembled at commit time.

6. The capture transport is the command line. A resident daemon
   speaking the same verbs over `simple-ipc` (as `fsmonitor--daemon`
   does) is deferred; it is a transport, not a capability, and creates
   no events an editor does not already expose.

Roadmap
-------
Each step is implemented and reviewed on its own:

1. Formats and library: the record formats, `provenance.c` on top of
   `notes.c`, and `provenance show`/`verify`.

2. Capture: the journal, `git stamp`, the attribution walk, and
   commit integration in a single ref transaction, including
   `--session` and the advice message for commits made without it.
   Adapters for particular agents live in a separate repository and
   are not part of this series.

3. Viewing: `--provenance` for `diff`, `show`, `log` and `blame`;
   pretty-format placeholders.

4. Transfer: default refspecs, merge on fetch, push with retry.

5. Rewrites: (a) remapping in amend, rebase and cherry-pick, with
   lines taken from commits without records marked `UNKNOWN`;
   (b) `adopt` for foreign rewrites, the marks of lines a revert
   restores taken from a blame of the parent, the records of a fixup
   or squash finished by a hand-run `git commit`, and those of
   `cherry-pick --no-commit` (done).

6. Hardening: `purge`, `fast-export`/`fast-import` and `format-patch`
   support, recording the conflict resolutions of merge commits, the
   query cache, a CI bot.

7. Deferred: the stamp daemon.

Alternatives Considered
-----------------------
A new object type carried by commits::
	Pack type 5 is the last free slot in the 3-bit type field. A new
	type touches the type table, `index-pack`, `unpack-objects`,
	`pack-objects`, bitmaps (which keep per-type bitmaps), the
	commit-graph, `fsck`, `cat-file`, the object filters and the
	SHA-1/SHA-256 converter, and every stock Git peer and hosting
	service rejects packs that contain it. Rejected: it breaks the
	migration goal outright.

A new commit header pointing at a provenance tree::
	Stock Git parses and accepts commits with unknown headers, but it
	does not follow the pointer: it does not transfer the tree, does
	not keep it alive and does not verify it, so a stock `gc` or a
	push through a stock server silently drops the data. The pointer
	is part of the commit id, so correcting or purging provenance
	rewrites history, and stock `rebase` drops the header. Guarding
	this with a repository format extension would make every stock
	Git refuse to open the repository. Rejected as storage.

Commit message trailers::
	Survive rewrites but clutter every message, cannot hold line
	maps, and make reasoning unredactable. Rejected.

Files committed with the code::
	Survive everything, including a host's squash merge, but add
	noise to every diff and pull request and conflict on every merge.
	Rejected.

Records under a ref, keyed by commit (the notes model)::
	Chosen. No change to the object, pack or wire formats; mutable
	and separable; needs remapping on rewrite, which anchors make
	recoverable.
